# Lead Intelligence MVP — Data Contract and Build Gate

**Parent architecture:** `docs/architecture/vanta-agent-operating-system.md`  
**Target:** Abuja Property Lead Intelligence / AutomaSuite LeadGen Pro foundation  
**Status:** Design note only; no schema has been applied and no application code has been changed.

## 1. First-release boundary

The first implementation must prove one controlled journey:

1. An authorised user starts a lead-discovery task.
2. The system records the requested geography, lead type, source scope and constraints.
3. A worker discovers candidate records only from permitted sources.
4. Each candidate is normalised and deduplicated.
5. Evidence and uncertainty are stored separately from the lead profile.
6. A qualification recommendation is generated with reasons and missing information.
7. A human reviews the recommendation and any proposed outreach.
8. Approved follow-up is recorded; sending remains a separate permissioned action.

Do not begin with a general-purpose agent marketplace, unrestricted browser agent, autonomous bulk messaging, or multi-brand shared workspace.

## 2. Canonical lead record

The first UI/API contract should use these fields:

| Field | Meaning | Rule |
|---|---|---|
| `id` | Internal UUID | Generated by database |
| `workspace_id` | Owning workspace | Required; enforced by RLS |
| `full_name` | Contact name | Nullable until verified/available |
| `company_name` | Organisation | Nullable |
| `phone_e164` | Normalised phone | Nullable; preserve original separately if needed |
| `email` | Email address | Nullable |
| `lead_type` | Buyer, seller, agent, developer, other, unknown | Controlled enum/check |
| `source` | Discovery source | Required |
| `status` | New, Researching, Qualified, Contacted, Nurturing, Converted, Not a fit | Controlled values |
| `intent_level` | Unknown, Low, Medium, High | Recommendation, not fact |
| `score` | 0–100 | Explainable and recalculable |
| `next_action` | Suggested next step | Human-readable |
| `created_at/updated_at` | Timestamps | Database-managed |

The existing schema is owner-scoped rather than workspace-scoped. Before multi-user/workspace access is introduced, explicitly decide whether the MVP remains single-owner or upgrades to workspace membership. Do not bolt on workspace UI while keeping ambiguous owner-only authorization.

## 3. Evidence is a first-class record

Every material discovery or qualification claim should be backed by a separate evidence record:

- `lead_id`
- `workspace_id`
- `source_type` and `source_url`
- `source_name`
- `observed_at`
- `captured_at`
- `evidence_excerpt` or a minimal structured observation
- `claim_type`: fact, inference, unknown, user-provided
- `confidence` with a documented meaning
- `verification_status`: unverified, corroborated, rejected, stale
- `reviewed_by` and `reviewed_at`, when reviewed

Never store a model-generated inference as a verified fact. Store source evidence and derived interpretation separately. Respect source terms, privacy, contact consent and retention requirements.

## 4. Qualification contract

A qualification result should be structured, not just a free-form score:

- buyer/seller/agent/developer/other/unknown role
- stated purpose and property interest
- location preference
- budget range and currency, only when supplied or verified
- purchase/sale timeline
- decision-maker status, if known
- key constraints and objections
- confidence level
- missing information
- evidence references
- recommended next action
- explanation of why the recommendation was made

Unknown values remain null/unknown. Do not infer budget, intent or readiness from a person's job title, profile photo, social activity or assumed wealth.

## 5. Data integrity and tenant isolation review

The current repository migration creates `leads`, `lead_activities`, `campaigns` and `lead_signals` with `owner_id` RLS. Before applying it to a dedicated project, review these points:

1. **Parent ownership:** ensure an activity or signal cannot reference a lead owned by another user. Use composite uniqueness/FKs such as `(id, owner_id)` on leads and matching composite foreign keys from child tables, or equivalent database-enforced constraints.
2. **Workspace model:** choose owner-only MVP or workspace membership before implementing shared teams. If workspace-based, add workspace IDs and membership-based policies consistently across every tenant-owned table.
3. **Policy naming and migration safety:** migrations should be repeatable in a fresh dedicated database; avoid relying on a partially configured shared project.
4. **Audit trail:** status changes and consequential edits should create immutable activity/audit events, not merely overwrite the current row.
5. **Evidence ownership:** evidence must be scoped to the same workspace/lead and protected by RLS.
6. **Unique contact keys:** email/phone deduplication must handle nulls, formatting and shared business contact numbers without incorrectly merging people.
7. **Service role:** privileged server operations must validate the caller and workspace explicitly; never expose service-role credentials to browser code.

No migration should run until the dedicated Supabase project identity, region, owner and isolation are verified.

## 6. Agent run and tool-call contract

Every run should persist:

- run ID, workspace, initiating user and request
- immutable agent version and prompt/config hash
- status, start/end times and bounded execution limits
- input and output references (avoid storing unnecessary sensitive payloads)
- step sequence, retries and checkpoint references
- tool name, validated arguments, permission decision and result summary
- evidence references
- approval request, approver, decision and timestamp
- idempotency key for any side effect
- error classification and safe retry eligibility

A tool call must be rejected if it is not registered, not enabled for that agent version, outside the workspace scope, or missing the required approval. Tool output is untrusted input and must not alter system policy.

## 7. Lead discovery MVP acceptance test

A test run is successful only when all conditions hold:

- It records the requested search scope and permitted sources.
- Each returned candidate has a source and observation timestamp.
- Missing phone/email details are labelled unavailable, not fabricated.
- Duplicate candidates are flagged or merged using a reviewable rule.
- Buyer intent is not asserted without evidence.
- Qualification lists unknowns and the next best diagnostic question.
- A draft message is contextual and contains no unsupported property claims.
- No message is sent without an explicit approval event.
- A run can be retried without duplicating leads or external messages.
- Every material decision is visible in the run audit trail.

## 8. Build and deployment gate

The application baseline is not yet verified green. The known Vercel status is a lint/type-related failure, but the exact build output could not be retrieved through the currently connected Vercel integration (deployment listing returned permission denied; log lookups returned not found).

Before code remediation:

1. Obtain the exact failed deployment or CI job logs.
2. Identify the exact command, file, line and dependency context.
3. Reproduce using the repository's intended Node version and package manager.
4. Pin dependencies and commit the appropriate lockfile.
5. Fix the root cause; do not disable lint/type checking to obtain a green build.
6. Run lint, typecheck and production build on the isolated branch.
7. Validate an isolated preview before any production promotion.

The root package manifest currently has no explicit `typecheck` script, and the inspected root had no npm, pnpm or Yarn lockfile. The CI workflow uses Node.js 20, `npm install`, lint and build. Confirm package-manager intent and resolve reproducibility before changing the workflow.

## 9. Explicit non-goals for this milestone

- No KSI Intelligence or DPF data, credentials, inventory or deployment reuse.
- No autonomous outbound WhatsApp/email.
- No bulk scraping or bypassing source access controls.
- No unverified property listings, prices, title documents or availability claims.
- No production database migration or deployment.
- No broad browser automation before tool permissions, audit and recovery are proven.
